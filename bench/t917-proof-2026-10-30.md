## Panel open questions OQ-2 and OQ-3: two metadata values at full precision

Read from the real Glimmer file during this same window, at the
critic panel's request. Keys enumerated with llama.cpp's own
`llama-gguf` (build-vulkan2/bin/llama-gguf, read mode, 32 kv
pairs); values read from the GGUF header with a stdlib Python
parser that prints the raw bits (gguf_meta.py, kept in the run's
staging tree). Both tools agree on the key names and order.

- **OQ-2, attention RMS norm epsilon.** Key
  `muse-glimmer.attention.layer_norm_rms_epsilon` (kv[11], GGUF
  type FLOAT32): **9.999999747378752e-06**, raw f32 bits
  `0x3727c5ac`. That is exactly the f32 nearest 1e-5, so the
  rebuild's asserted 1e-5 (crates/muse-glimmer/src/config.rs,
  which reads this key and asserts the parsed value within 1e-9
  of 1e-5) is confirmed against the primary source: the file
  carries 1e-5 at f32 precision, nothing else.
- **OQ-3, logit scale.** Key `muse-glimmer.logit_scale`
  (kv[15], GGUF type FLOAT32): **0.1961161345243454**, raw f32
  bits `0x3e48d2ab`. The code carries 0.19611613
  (crates/muse-glimmer/src/config.rs doc and test constant,
  asserted within 1e-6; actual difference 4.5e-9), which is this
  f32 rounded to 8 decimal places, and the loader reads the
  value from the file itself, so the runtime uses the exact f32.
  The dissection's printed 0.1961 is a 4-decimal display rounding
  of the same value. No discrepancy.
- Neighbouring value, for the record: kv[14]
  `muse-glimmer.final_logit_softcapping` = 20.0 exactly (f32
  bits `0x41a00000`), matching the softcap 20.0 the config doc
  states.

## The T-9.16 defects this run caught, and their fixes

The first chat request of the run failed before generation, and
the two defects below are why. Both were real defects in the
T-9.16 implementation scope; both are fixed minimally and
committed; proof 4 at the end of this note is the re-run that
passes against llama.cpp.

### Defect 1: the renderer could not render the model's own template (fixed in 9379364)

The platform answered the first chat request with a named
`chat_template_error`: `chattemplate: unsupported construct:
{% %}`. The Glimmer file's template is the full ATEM Jinja
template (9,992 chars, now kept as the renderer fixture
platform/internal/chattemplate/testdata/glimmer-atem.jinja): it
uses macros, `namespace()` state, `{% set %}` including
namespace attribute mutation, `defined` tests, `join` /
`replace` / `lower` filters, and a header comment whose text
contains tag lookalikes. The bounded renderer from 311fa1b
covered none of that, so the file's own template was outside
the subset.

Fix (commit 9379364): the renderer now supports `{# comments #}`,
macros, set including namespace attribute mutation, general
`{% for x in expr %}` with loop.index / index0 / first / last /
length and pair targets, value-typed expressions with
undefined-name semantics (falsy, answers `is defined`, refuses
by name when printed), list and mapping literals, dynamic
subscripts, dict.get / str.split / dict.items, the tests
defined, none, string, boolean, number, mapping and iterable,
inline conditionals, and the trim / lower / replace / join
filters. Constructs still outside the subset (length and tojson
filters, unknown method calls, printing a boolean) still refuse
by name. The real template renders byte-exact in unit tests.

### Defect 2: every chat prompt ran with two BOS ids (fixed in 819b1ae)

With the renderer fixed, a chat request reached the engine, and
the engine's logged prompt ids began **[200000, 200000,
200022, ...]**: the rendered template starts with the bos_token
text, which tokenizes to the BOS id 200000, and the engine then
prepended the BOS id again because the file sets
add_bos_token. llama.cpp's tokenizer drops the duplicate in
exactly this case (llama-vocab.cpp), so our ids could never
have matched llama.cpp's until this was fixed.

Fix (commit 819b1ae): a shared `assemble_prompt_ids` helper in
crates/itak-engine prepends BOS only when the tokenized body
does not already begin with it, used by generate and embed
alike. Unit-covered (prepend, already-present, not-asked,
no-BOS-id, empty body); cargo test -p itak-engine 30/30. The
post-fix engine log for the same request begins [200000,
200022, ...]: one BOS.

### Defect 3: the environment lacked strftime_now, so the rendered prompt missed the Current date line (fixed in af21f92)

Proof 4's first comparison (after fixes 1 and 2) put our 52 ids
next to llama.cpp's 63 for the same messages. The two sequences
were identical everywhere except one 11-id segment in
llama.cpp's system block: `\nCurrent date: 2026-10-31.`. The
ATEM template prints that line when a `current_date` variable
is supplied OR when `strftime_now` is defined in the
environment (template lines 115-118). llama.cpp's minja runtime
defines `strftime_now` from the host clock; our environment
defined neither variable nor function, so the guarded branch
rendered nothing, silently.

Fix (commit af21f92): the renderer registers `strftime_now` as
a global builtin, mirroring the reference environment. It
answers the defined test, formats the host clock through a
strftime subset (%Y %y %m %d %H %M %S %j %%), and refuses
unknown specifiers and printing the function itself by name.
Params.Now pins the clock for tests; the Glimmer golden now
carries the date line with a pinned date, and the
caller-system golden is unchanged (the date block lives in the
template's default-system branch only).

## Proof 2 (T-9.14 two concurrent chat requests): PASS

Two chat completions fired at the same moment at one engine
running `--slots 2`, through the platform:

- A: user "Capital of France? One word."
- B: user "Capital of Japan? One word."

Both at temperature 0, model "Muse Glimmer Hf". The engine log
shows both generate starts in the same millisecond, each with
prompt_tokens=52, and the two engine-side prompt id sequences
differ at exactly one position (11698 "France" vs 11197
"Japan"), proving each slot held its own prompt and KV state.

Debug evidence: a poller captured /debug every 20 s for the
whole first run: 589 snapshots, **588 with slots=2, active=2,
queued=0** (max_queued 8, busy true, chat_template "engine",
supervisor running with 0 restarts). Extract:
`proof2/debug-extract.txt` in the staging tree.

Run 1 (max_tokens 2): both complete, finish_reason length,
wall 11,782.31 s for the pair (requests 7 s apart at the end).
Both contents were ` to=self`: identical, and correct as far as
they go, because this model's templated reply opens with the
ATEM recipient header before any answer text. Identical
2-token prefixes do not by themselves demonstrate independent
outputs, so the pair was re-run deeper rather than argued
about.

Run 2 (max_tokens 6): both complete, finish_reason length,
wall 12,024.91 s, finishing 0.8 s apart. Contents:

- A: ` to=self<|message|>Capital of France`
- B: ` to=self<|message|>Capital of Japan`

The completions diverge exactly at each prompt's own country:
the recipient header, then the message marker, then the start
of an answer naming the country that slot was asked about.
Two concurrent jobs, one engine, independent correct outputs.
Artifacts: `proof2/` and `proof2b/` in the staging tree.
