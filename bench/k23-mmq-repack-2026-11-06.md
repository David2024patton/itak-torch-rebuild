# K23: the Q4_K MMQ staging repack - design, layout arithmetic, and the card verdict protocol

Lane `lane/k23-mmq-repack`, built 2026-11-06. State: code
complete and VM-gated (counts below); the card verdict
protocol is written and NOT yet run (the parent serializes
card time). The routing switch defaults OFF; nothing in the
shipped ladder changes with the switch unset.

## The problem, from the measurements

The prefill profile (`bench/prefill-profile-2026-11-05.md`)
put the Q4_K MMQ kernel (K13) at 4,199.9 ms of a 6,659 ms
GPU total for the 1,022-token prefill - 63.1% of GPU time
streaming at 46.4 GB/s against a card that streams a GEMV
at 649.5 GB/s in the same run. K13 compiles to the VGPR
256 cap. K22 attacked the register organization and hit
the same cap in compiled form (autopsy in
`bench/k22-mmq-2026-11-05.md`: VGPR 256, zero spills, LDS
41,984 B - ACO re-inflated the organization, steps 1-3
never ran). The parity extraction
(`bench/llama-parity-specs-2026-11-06.md`, gap 2) then
named the one structural difference left: the staging.
K13 stages a whole 256-element super-block column per
barrier round, scale pairs interleaved beside the data
they scale, one 65-word skew on the activation rows.
llama's MMQ stages in 128-element rounds, qs arrays
pitched with a skew, scale pairs split into their own
arrays. K23 copies that staging onto K13's organization
and changes nothing else, so whatever the card says is
attributable to the staging alone.

## What K23 is

A new env-gated Q4_K MMQ kernel
(`crates/wgpu-compute/src/kernels/k23_q4k_mmq.rs`) with
K13's tile coverage (64 output rows x 64 batch rows),
K13's thread organization (256 threads, sixteen
output-row groups by sixteen batch-row groups, a 4x4
sub-tile per thread, the `isum` array, scalar
`dot4I8Packed`, immediate per-sub-block folds in K13's
exact order and expression), K13's bindings, params,
prepare contract (batch 1..=64), and `[batch][out]`
output layout. A plan can swap K13, K22, and K23 without
moving a byte. The single design variable is the
staging, transcribed from llama's mul_mmq_cm1 (see the
layout arithmetic).

## Layout arithmetic, with llama citations

llama sources are the vulkan-shaders tree at llama.cpp
a7af149, verified sha256-identical between the server
tree and the VM mirror by the parity note.

**The round quantum.** `BK = 32` (mul_mmq_cm1.comp:89),
`BK_STEP = 4` (mul_mmq_cm1.comp:93, the non-`MUL_MAT_ID`
form): one staging round covers BK x BK_STEP = 128 K
elements. A Q4_K super-block column is 256 elements, so
a column is two rounds: stage, barrier, four sub-blocks
of dots, barrier, twice per column (K13: one round of
eight sub-blocks, two barriers per column; K23: four
barriers per column).

**The pitch.** `QPITCH = BK_STEP * (BK / 4) + 4 = 36`
(mul_mmq_cm1.comp:97). Each staged row segment holds 32
words of one round's qs data plus a 4-word skew.

**The split arrays** (mul_mmq_cm1.comp:99-110), with
llama's BM = BN replaced by this tile's 64:

| array | llama declaration | K23 declaration | bytes |
|---|---|---|---|
| w_qs | `buf_a_qs[BM * QPITCH]` (:99) | `array<u32, 2304>` (64 x 36) | 9,216 |
| x_qs | `buf_b_qs[BN * QPITCH]` (:106) | `array<u32, 2304>` (64 x 36) | 9,216 |
| w_dm | `buf_a_dm[BM * BK_STEP]` (:101) | `array<vec2<f32>, 256>` (4 x 64) | 2,048 |
| x_d | `buf_b_d[BN * BK_STEP]` (:107) | `array<f32, 256>` (4 x 64) | 1,024 |
| x_s | `buf_b_s[BN * BK_STEP]` (:110) | `array<f32, 256>` (4 x 64) | 1,024 |

Staged set total: **22,528 B**, against K13's 41,216 B
designed (41,984 B compiled class) and K22's 41,472 B at
the same tile. The set halves because a round stages
half the K span; the pitch adds 4 words per row per qs
array (512 B across both).

**A-side staged addresses.** llama's Q4_K
`block_a_to_shmem` (mul_mmq_cm1_funcs.glsl, the
`DATA_A_Q4_K` branch at :246, the function at :274)
writes `buf_a_qs[buf_ib * QPITCH + ks * (BK / 4) +
loadr * 2 + {0,1}]`, loadr in 0..4 walking the four
word-pairs of a sub-block's 8-word group; the staged
word is the raw Q4_K word masked `& 0x0F0F0F0F` for an
even sub-block or `(raw >> 4) & 0x0F0F0F0F` for an odd
one (the `block_a_load` nibble select on `ib % 2`).
K23's store is `w_qs[n * 36 + ks * 8 + loadr * 2 +
{0,1}]`, the same index arithmetic. The scale pair is
deposited by the loadr == 0 task at
`buf_a_dm[ks * BM + buf_ib]` in llama; K23 writes
`w_dm[ks * 64 + n]`. The VALUE keeps K13's convention
`(d * scale, dmin * min)`: cm1 stages
`(d * scale, -(dmin * min))` and subtracts in its fold,
K13's fold text carries the negation
(`acc += c.x * (dm.x * isum) - c.y * dm.y`), and K23's
fold text is K13's byte for byte, so the pair's sign
convention stays with the fold it feeds.

**B-side staged addresses.** llama's `block_b_load`
(mul_mmq_cm1_funcs.glsl, just above :529) loads
`data_b[ib_outer].qs[ib_inner * 2 + loadr]`, one ivec4
of a `block_q8_1_x4` group, loadr in 0..2 covering the
block's two 4-word halves; `block_b_to_shmem` (:529)
scatters its components to
`buf_ib * QPITCH + ks * (BK / 4) + loadr * 4 + 0..3` and,
on loadr == 0, writes `buf_b_d[ks * BN + buf_ib]` and
`buf_b_s[ks * BN + buf_ib]`. K23's store is
`x_qs[m * 36 + ks * 8 + loadr * 4 + c]` with
`x_d[ks * 64 + m]` / `x_s[ks * 64 + m]` on loadr == 0 -
the same arithmetic over K12's flat streams (see the
honesty paragraph).

**Consumption addresses.** Per sub-block ks of a round,
a thread reads `x_qs[m * 36 + ks * 8 + w]` and
`w_qs[n * 36 + ks * 8 + w]` for its 4x4 sub-tile,
`c = w_dm[ks * 64 + n]`, and
`dm = vec2(x_d[ks * 64 + m], x_s[ks * 64 + m])`.

**What the de-interleave means on our buffers.** The
gap note's phrase "de-interleaves the x4-packed Q8_1 B
layout into consumption order" describes llama's DRAM
format: `block_q8_1_x4` (types.glsl:267) groups four
Q8_1 blocks, their four (d, s) pairs collected in a
header array ahead of the qs words, each block's 8
words contiguous at `qs[8 * ib_inner ..]` (producer:
quantize_q8_1.comp:87 and :116). The scalar
`block_b_to_shmem` (mul_mmq_funcs.glsl:651) pulls each
block's pair out of that header into its own staged
slot. Our K12 output is two flat streams - qs words in
plain (row, block, word) order, one scale vec4 per
block - so there is no group header to undo: within a
block, the permutation is the identity by construction,
and K13's own B-side staging (a flat coalesced copy) and
K23's scatter write the same qs values; they differ in
the staged ADDRESSES (pitched, split scales) and in
which scale array a pair lands in. The transcription's
structural content is the addresses, the split, the
pitch, and the round size - not a data permutation.
Anyone reading a K23 win or loss should read it as a
verdict on those, not on de-interleaving work our
buffers never needed.

## Computed bank analysis (analysis, not measurement)

llama's +4 skew is tuned for cm1's coopmat fragment
loads. What it does under K13's scalar consumption
mapping (4-row lane groups; addresses below are word
addresses, 32 LDS banks) is computable, and it is not
uniformly good:

- **Activation qs loads** (16 distinct addresses per
  instruction, row step 4 rows): K13's 65-word pitch
  gives step 260 = 4 mod 32, eight banks, a 2-way
  conflict. K23's full-column row pitch is 72 words
  (two 36-word round segments): step 288 = 0 mod 32,
  two banks, an **8-way conflict - worse**.
- **Weight qs loads** (2 distinct addresses): K13's
  unstaged-pitch 64 gives step 256 = 0 mod 32, same
  bank, 2-way. K23's step 144 = 16 mod 32, different
  banks, **conflict-free - better**. (K22's 65-word
  weight skew also lands conflict-free here.)
- **Weight pair loads** (2 distinct addresses): K13's
  `w_sm[n * 8 + sub]` gives step 32 = 0 mod 32, 2-way.
  K23's `w_dm[ks * 64 + n]` gives addresses 4 apart,
  different banks, **conflict-free - better**.
- **Activation pair loads** (16 distinct addresses):
  K13's `x_ds[m * 8 + sub]` gives step 32 = 0 mod 32 -
  all sixteen addresses in ONE bank, a **16-way
  conflict** on every dm load. K23's
  `x_d[ks * 64 + m]` gives step 4, four banks, a 4-way
  conflict - **better**, and the single largest
  computed improvement in the layout.

Net: the scale loads improve sharply, the weight qs
loads improve, and the activation qs loads - half the
dot loop's word loads - regress from 2-way to 8-way.
The sign of the total is genuinely not computable from
here; that is what the card protocol is for.

## Deliberately not copied

- **K22's register organization.** One design variable
  per experiment; K23 keeps K13's organization.
- **The scalar mul_mmq A-side interleave repack**
  (mul_mmq_funcs.glsl:530, the Q4_K branch):
  `vals0 | vals1 << 4` packing with per-dot shift
  extraction. It serves the scalar path's register-file
  consumption; the cm1 A side stages nibbles already
  separated, so the interleave has no consumer in this
  layout. Named here so a later lane can take it
  deliberately; gap 2's remaining piece after K23.
- **Coopmat and per-device tile specialization**: the
  coopmat feasibility note owns that question.

## Routing

`mmq_product_q4k` gains one rung: wide K15 (batch at
the wide threshold), then K22 under
`WGPU_COMPUTE_K22_MMQ=1`, then **K23 under
`WGPU_COMPUTE_K23_MMQ=1`**, then K13. The resolver is
the K22 pattern exactly (exact value `1` after trim;
everything else off; unit-tested both ways). The
backend builds the pipeline at construction regardless
of the switch and prints `mmq k23 config: enabled=...`
through the diag log channel, so a shader defect fails
at startup, not on first routed use. Diag stamp from
birth: `k23_q4k_mmq` (DispatchMeta at prepare, K22's
shape). ProjCall gains `MmqK23Q4K` with encode,
dispatch-count, and `kernel_name() = "k23_q4k_mmq"`
arms; it is classified quantized (it carries the K12
quantize), like every MMQ form. With the switch unset
the ladder is the shipped ladder exactly.

## Server verdict protocol

Preconditions: card cleared per David's standing GPU
order (tenants stopped, restored after), phase lock
held, staging synced to the lane commit and
hash-verified, `prefill_profile` available. Run on the
RX 7900 XTX (gfx1100, RADV Mesa 26.0.8) - the same card
and driver class as every recorded comparison number.

0. **Shader autopsy first.** Compile K23 in isolation
   (the `shader_compile` k23 leg) under
   `RADV_DEBUG=shaderstats,asm,cs` with a private
   `MESA_SHADER_CACHE_DIR`. Read VGPR, spilled VGPR,
   scratch, LDS. The numbers that matter: VGPR against
   K13's/K22's 256 cap, spills and scratch against
   their zero, LDS against K13's 41,984 B compiled
   class (K23's designed set is 22,528 B; the compiled
   line should land on it). If VGPR reads 256 AND the
   compiled LDS is not materially below K13's class,
   the staging changed nothing the compiler prices;
   record both lines and still run step 1 (correctness
   is owed regardless), but steps 2-3 become
   confirmation, not a flip case.
1. **Correctness on the card.** `cargo test -p
   wgpu-compute --test k23_mmq` must actually execute
   (not skip): reference and K13 parity at batches 16,
   32, 64 and the 62-row tail, plus the band refusals.
   Also `resident_session` with
   `WGPU_COMPUTE_K23_MMQ=1`: identity + golden on the
   real file before any speed number is read, and the
   diag CSV for the run must show `k23_q4k_mmq` stamps
   on the Q4_K projections (the exposure check: K23
   unrouted would be a silent no-op A/B). The K12
   quantize dispatch counts stay identical to the
   control run; only the product kernel name changes.
2. **Kernel-level A/B.** Through `prefill_profile`:
   the same 1,022-token prompt, diag timing on, K23 env
   on vs off, same session conditions. Compare the
   `k23_q4k_mmq` row against K13's recorded 4,199.9 ms /
   46.4 GB/s and the total GPU time against the
   profile's 6,659 ms. Report achieved GB/s beside
   K13's line.
3. **Prefill A/B, session level.** `glimmer_generate
   --gpu` wall on the same prompt, env on vs off, three
   runs each, timing-off walls compared against the
   current recorded 6,330 ms (post host-gap fix). The
   profile's two historical runs agreed to 0.5%; a
   difference inside that band is a wash.
4. **No-leak check.** With the env unset, plain decode
   and the spec verdict harness must reproduce their
   recorded numbers, and a diag run must show zero
   `k23_q4k_mmq` stamps. K23 is unreachable with the
   switch off, so any movement is a routing leak, not a
   kernel result.

**Decision rule, written in advance.** The default
stays OFF unless one of two cases holds, with step 1
green in both: (a) step 0 shows an autopsy improvement
- VGPR off the 256 cap with zero spills and zero
scratch, or the compiled LDS materially below K13's
41,984 B class with no spills/scratch regression
(noting the occupancy caveat in lose-condition 5: LDS
alone does not raise occupancy while VGPR pins the
register file, so an LDS-only improvement supports a
flip only together with a step 2 or 3 win); or (b)
step 2 or step 3 shows a material prefill win - the
Q4_K MMQ line or the wall faster by more than the
0.5% run-agreement band, with correctness green.
Otherwise the flag stays off and the numbers are the
finding, recorded in this note like K22's verdict was.
Any default flip is a separate change with this note's
numbers attached.

## What could still make K23 lose to K13 on the card

Honest list, in the order I would bet on them:

1. **ACO still caps the registers at 256.** K23 keeps
   K13's organization, and K13 compiles to the cap;
   K22 proved the allocator does not take source-level
   hints from this codebase. A smaller staged set does
   not by itself give the allocator fewer live values:
   the `isum` array, the 64 staged-word lets per
   sub-block, and the accumulators are unchanged. Step
   0 exists to answer this cheaply.
2. **The activation-qs bank regression is real and the
   scale-load wins are not.** The computed analysis
   above: xv loads go from a 2-way to an 8-way
   conflict, and they are half the dot loop's LDS word
   loads; the dm improvement (16-way to 4-way) touches
   one load per (row, sub-block) against eight word
   steps of qs loads. If LDS throughput is the binding
   constraint, K23 is slower than K13 by construction.
3. **The repack costs staging instructions.** Each raw
   weight word is read twice - once per nibble half,
   in cm1's per-sub-block load shape - where K13 reads
   it once and extracts both halves in one task. The
   pitched scatter and the split d/s deposits add
   address arithmetic per staged word, and barriers
   double (four per column against K13's two), adding
   serialization points where the whole workgroup
   waits on the slowest staging task.
4. **The split layout fits WGSL's storage model
   worse than it fits GLSL's.** cm1's arrays are plain
   shared arrays; in WGSL the fold assembles dm from
   two separate scalar loads (x_d, x_s) where K13
   loads one vec2, and five workgroup arrays (against
   K13's four) mean more base-address registers held
   across the inner loop. Small, but it pushes against
   lose-condition 1.
5. **The LDS halving cannot pay alone.** At VGPR 256,
   a 256-thread workgroup occupies 256 x 256 x 4 B =
   256 KB of register file - the whole CU file - so
   occupancy is one workgroup per CU no matter how
   small LDS gets. The smaller set only converts to
   occupancy if VGPR also falls; read step 0's pair of
   lines together, never the LDS line alone.
6. **The B staging's global-load pattern is less
   coalesced.** Tasks stride by activation row (32
   useful bytes per task span) where K13's flat copy
   reads contiguously; worst case about 4x cacheline
   waste on activation staging reads. Bounded small
   (the activation tile is 16 KB per column pass), but
   it is a real cost the flat copy does not pay.
7. **Half the lookahead per round.** A round holds
   four sub-blocks of independent dot work against
   K13's eight; inside a round the scheduler has half
   as much independent work per thread to hide LDS
   latency with, at the same per-thread register
   budget. If latency hiding was part of K13's rate,
   the round structure taxes it.
