# GGUF file image is memory-mapped, 2026-11-05

PLAN T-2.1, landed on `lane/gguf-mmap`. `GgufFile::open` no longer
reads the whole GGUF into anonymous RAM. This is reduction #2 of
the phase B footprint audit (bench/phase-b-footprint-2026-11-05.md):
the audit's rows 1 and 3, the target and draft file images held via
`std::fs::read`, were 17.11 GiB of the 32.70 GiB kill-window
residency that got the speculative harness OOM-killed nine times.

## The change

- `crates/gguf/src/file.rs`: the `GgufFile.bytes: Vec<u8>` field is
  now a private `ImageBacking` enum, `Owned(Vec<u8>)` or
  `Mapped(memmap2::Mmap)`, with one `as_slice()` accessor. `open`
  and `from_bytes` split into constructors over a shared private
  `parse(backing)`; the parse itself (header walk, metadata,
  tensor directory, bounds checks) is byte-for-byte the code that
  ran before, reading through the slice either backing serves.
- `open` maps the file read-only. One special case: a zero-length
  file cannot be mapped (memmap2 refuses it), so `open` parses an
  empty owned image instead, which produces exactly the named
  failure the in-memory path has always produced for an empty file
  (`Truncated` reading the magic) rather than an Io mapping error.
- `crates/gguf/src/lib.rs`: `#![forbid(unsafe_code)]` becomes
  `#![deny(unsafe_code)]`. The map call is the crate's only unsafe,
  isolated in `file::map_file` under an item-level
  `#[allow(unsafe_code)]` with the full safety contract written on
  it: the file must not be truncated or rewritten while a
  `GgufFile` opened from it is alive (reads past a truncated end
  fault with SIGBUS instead of failing named; that is inherent to
  mmap and is the same assumption llama.cpp's reader makes). Model
  files are immutable during a run and replaced by rename between
  runs; `deny` still makes any second unsafe block in the crate a
  lint error.
- Dependency: `memmap2 = "0.9"` (resolved 0.9.12), added to the
  gguf crate only. It was not in this workspace's lockfile before;
  it is the standard mapping crate, it was already present in this
  machine's cargo registry cache, and there is no std API for file
  mapping. The lockfile gained exactly one package (memmap2); its
  platform dependencies (libc, windows-sys) were already in the
  lock via other workspace crates. The gguf crate previously had
  zero dependencies; the parser, metadata, and dequantizers remain
  std-only.

## API compatibility

- The public API did not change: `open`, `from_bytes`, `file_len`,
  `tensor_bytes`, `load_f32`, `metadata`, and the rest keep their
  signatures and semantics. All 70 `GgufFile::open` / `from_bytes`
  call sites across the workspace compiled and passed unchanged;
  no consumer was edited.
- Alignment is not part of the contract and never was: consumers
  receive `&[u8]` and read it byte-wise (a workspace-wide search
  finds no bytemuck, `align_to`, or typed cast over tensor bytes;
  a `Vec<u8>` only ever guaranteed alignment 1 anyway). GGUF
  tensor data offsets keep the file's own alignment (32 by
  default) from the mapping base, as they did from the Vec.
- No consumer needed a new owned copy because of this change. The
  one pre-existing copy, the loader adapter's per-tensor
  `Arc::from` (audit row 2, 15.59 GiB), is untouched: it is
  reduction #3's seam (zero-copy tensor views), a separate task.
  With only this fix, that copy becomes the whole remaining anon
  footprint, which is the point: either reduction alone suffices.

## Failure behavior (pinned by crates/gguf/tests/open.rs)

Five new tests run the same fixture through both paths and compare
observables, including the Display text of errors:

- missing file: `Io` with `ErrorKind::NotFound`, as `fs::read`
  produced before.
- empty file: `Truncated { context: "magic" }`, Display-identical
  to `from_bytes` (this pins the zero-length fallback above).
- bad magic: `BadMagic`, Display-identical to `from_bytes`.
- truncated file at two cut points (mid-directory and mid-data):
  the error text is identical between `open` and `from_bytes` at
  both cuts.
- full parity: version, file_len, data_start, alignment, metadata,
  tensor names and order, per-tensor raw bytes, and `load_f32`
  values all equal; a missing tensor still names `MissingTensor`.

Not tested: a file shrinking after it is mapped. That cannot be
tested without racing the mapping (the read faults at the OS
level, it does not return an error), so it is covered by the
written contract on `open` and `map_file` instead, per the task's
terms.

## RSS evidence (this VM)

`crates/gguf/examples/mmap_rss.rs` writes a synthetic GGUF with one
F32 tensor of the given size, then reports /proc/self/status at
each phase. A hard in-test RSS assertion would be flaky (parallel
tests share a process), so the evidence is this example plus the
recorded runs, per the task's allowance. Commands:

```
cargo run -p gguf --release --example mmap_rss -- 512  <dir>
cargo run -p gguf --release --example mmap_rss -- 1024 <dir>
```

(`<dir>` must be a volume that can hold the file; this VM's /tmp
is a 512 MB tmpfs, so the runs used the workspace volume.)

512 MiB tensor:

| phase | VmRSS | RssAnon | RssFile |
|---|---|---|---|
| start | 2.2 MiB | 0.1 MiB | 2.0 MiB |
| mapped open | 2.3 MiB | 0.1 MiB | 2.1 MiB |
| mapped touch 3 pages | 2.3 MiB | 0.1 MiB | 2.2 MiB |
| mapped touch every page | 487.7 MiB | 0.1 MiB | 487.6 MiB |
| mapped dropped | 2.2 MiB | 0.1 MiB | 2.1 MiB |
| owned read + from_bytes | 514.2 MiB | 512.1 MiB | 2.1 MiB |

1024 MiB tensor: same shape. Mapped anon stays 0.1 MiB at every
phase; the every-page touch reaches VmRSS 1014.0 MiB, all of it
RssFile (1013.8 MiB); the owned path reads RssAnon 1024.1 MiB.

Reading: opening and fully reading a mapped 1 GiB model costs
0.1 MiB of anonymous RSS at both sizes, flat; the owned path costs
exactly the file size in anonymous RSS. Mapped pages count in
VmRSS as file RSS: present while touched, evictable under
pressure, and absent from the anon-rss figure the OOM killer
acts on (the kills were recorded in anon-rss).

## Expected phase B peak after this fix

Audit arithmetic, unchanged rows: row 2 (the extracted `Weights`
copy, 15.59 GiB) plus the bounded residue (about 0.4 GiB) is all
that remains in the anonymous tally at the kill window: about
16 GiB, against the observed 32-38 GB-free nights that killed the
old code at 35.5 GB. Phase B should now complete at a normal RAM
moment on the loaded server, without waiting for a 40 GB window.
