# GPU trace tooling: SQTT, hang dumps, host telemetry, canary (2026-11-06)

Lane: lane/gpu-trace-tooling, based on main 2f8b3ae.
Tooling and documentation only: one new bench script
(`bench/gpu-trace.sh`) and this note. No engine code
touched, no server GPU jobs run in this lane (card time
is serialized by the parent and several verdict lanes
are queued ahead of the first traced run).

**Verdict in one line:** the four visibility forms the
2026-11-04 streaming-rate research identified but nobody
wired into a repeatable tool — SQTT thread traces, hang
forensics dumps, a host telemetry timeline, and a
bandwidth canary — now run as one command around any
bench binary and file themselves as one run directory;
the wrapper and its telemetry sampler are demonstrated
end to end on the build VM (which has no GPU, so the
trace-side artifacts degrade honestly there and the
server run below is the first real capture).

## What already existed, and what was missing

- Per-dispatch GPU timing (the diag system,
  `WGPU_COMPUTE_DIAG=timing` + `WGPU_COMPUTE_DIAG_OUT`):
  says how long each kernel ran. It cannot say where the
  card's waves stalled while they ran.
- The shader autopsy (`bench/shader-autopsy.sh`):
  captures the compiled form (RADV_DEBUG
  shaderstats/asm) of every kernel family, but only
  inside dedicated autopsy sessions, never attached to
  an ordinary measured run.
- Host readings (VRAM from amdgpu sysfs counters,
  process RSS from /proc) were taken by hand during
  verdict sessions and survive only in those notes'
  prose: the cleared-card guard numbers, the phase-B
  footprint audit's 34.6 GB anon-RSS kill signature.
  Nothing sampled them during a run.
- Missing entirely until now: SQTT captures (never
  taken on this stack), a hang-forensics readiness
  position (the one production symptom on record, the
  wide-MMQ session hang of 2026-11-04, was diagnosed
  after the fact from compiled form alone), and a
  same-session bandwidth canary to set kernel stream
  rates against.

## The tool

`bench/gpu-trace.sh LABEL [--] COMMAND [ARGS...]` runs
COMMAND with the visibility env applied to the child
only (via env(1)) and creates
`bench/traces/<UTC stamp>-<label>/`:

| artifact | what it answers |
| --- | --- |
| stdout.log, stderr.log | what the run said, streamed live and filed |
| `*.rgp` + rgp-sources.txt | where the card's waves actually stalled (below) |
| shaderstats.txt, asm/ | the compiled form of whatever this run actually compiled |
| telemetry.csv | was the host or the card the wall (below) |
| canary.txt | the honest ceiling for the day (below) |
| manifest.txt | command, env applied, git SHA, Mesa version if readable, exit code, inventory |

plus one appended line per run in `bench/traces/INDEX.md`.
The wrapper preserves the command's exit code exactly
and never times the command out.

### SQTT: where the waves stalled

Env: `MESA_VK_TRACE=rgp` with `MESA_VK_TRACE_PER_SUBMIT=1`.
These are the current correct switches (Mesa envvars
documentation, verified live by the 2026-11-04 research):
RADV's built-in capture writes .rgp files that open in
AMD's Radeon GPU Profiler, which shows wavefront
occupancy over time, per-instruction timing, pipeline
and barrier stalls, cache behaviour, and (Mesa 26-era
RADV) LDS bank-conflict counters on GFX11. That is the
view that separates the streaming-rate hypotheses the
diag timings cannot: not enough waves in flight vs
long memory latency vs LDS-path stalls vs barrier
lock-stepping. `MESA_VK_TRACE_PER_SUBMIT` is Mesa's
documented knob for compute-only workloads, which is
what every bench binary here is. The old
`RADV_THREAD_TRACE` controls were removed from Mesa;
a correction on exactly this point was delivered with
the 2026-11-04 research report, and this script does
not use them.

Mesa's dump directory is not settable through a
documented env var, so after the child exits the
wrapper sweeps the working directory, /tmp, and $HOME
for .rgp files newer than the run's start marker and
moves them into the run dir, recording each file's
origin in rgp-sources.txt. The sweep is the reason
traced runs belong inside the phase lock like every
other card session: the lock is what makes "newer than
the marker" mean "ours".

The child also gets a private `MESA_SHADER_CACHE_DIR`
inside the run dir (a caller-set value is kept and
recorded). Without it, a warm shared cache compiles
nothing and RADV prints no stats or disassembly at
all — the same cold-cache discipline the autopsy uses.

### Hang forensics: the wedge kit

`GPU_TRACE_HANG=1` adds `hang` to the child's
RADV_DEBUG. RADV_DEBUG=hang makes RADV dump its state
(and umr register/wave/ring dumps, unless disabled)
when a queue hangs, which is the evidence a wedged
card can still give. The standing example is the
wide-MMQ (K15/K16) session hang of 2026-11-04: the
session wedged once, and the cause (1,041-1,213
spilled VGPRs, 78-86 KB scratch in the compiled wide
forms) was convicted a day later from the autopsy,
because no hang capture existed at the moment of the
wedge. That diagnosis should never again depend on
reconstructing the moment afterwards.

The wrapper is built for this case: it never times
the child out, and telemetry keeps sampling while the
card is wedged, so the timeline leading into the hang
survives. The operator kills the child; the wrapper
files everything and preserves the kill as the exit
code.

**Standing rule, from this note forward: any future
card hang gets exactly one hang-forensics rerun —
the same command under `GPU_TRACE_HANG=1
bench/gpu-trace.sh <label>-hang -- <command>` —
before anyone reboots the host, resets the card, or
changes the code under test.** One rerun, because the
first hang's own artifacts (telemetry up to the wedge,
the hung session's logs) plus one instrumented
reproduction are the evidence set; repeated wedging
of the card for curiosity is not.

### Telemetry: host or card

An embedded python3 sampler (no new dependencies;
python3 is already the bench scripts' extractor)
samples for the wrapped process's lifetime at about
10 Hz (`GPU_TRACE_INTERVAL`, default 0.1 s):

- `vram_used_bytes`: the big card's
  `mem_info_vram_used` (device chosen by the bench
  runners' existing rule, VRAM total over 20 GB) —
  the same counter the cleared-card guards read.
- `proc_rss_kib`: the wrapped process's VmRSS from
  /proc/<pid>/status. The process only; children it
  forks are not summed (declared in the CSV header).
  This is the column that would have drawn the phase-B
  footprint curve (a ~35 GB anon-RSS climb into the
  OOM killer) as it happened instead of after.
- `load1`: /proc/loadavg field 1.
- `gpu_edge_temp_millic`, `gpu_power_microw`: the
  amdgpu hwmon's temp1_input and power1_average —
  the throttling evidence: a run that slows while
  temperature or power sits at the cap is a different
  finding from a run that slows cold.

Absent sources degrade honestly: the column stays
empty and the CSV header names the source ABSENT.
Lining the timeline up against the diag output is by
run window: manifest.txt records start/end epochs,
the telemetry rows carry epoch seconds, and the diag
CSV's per-kernel totals (plus the per-dispatch
`[wgpu-compute-diag]` lines the wrapper files in
stderr.log) describe the same window.

### Canary: the ceiling for the day

After the child exits — never concurrently, so the
canary cannot steal bandwidth from the measured run —
the wrapper runs vkpeak, or clpeak if vkpeak is
absent, into canary.txt (180 s timeout). That is the
same-session practical ceiling to set kernel stream
rates against, replacing the habit of comparing a
run against numbers from other days: the recorded
references are the card's 960 GB/s spec, GEMV's
649.5 GB/s measured in the 2026-11-05 prefill
profile, and the MMQ pair's 43.5 GB/s in the same
profile. If neither tool is on PATH, canary.txt
records the absence and names those references
instead of inventing a reading.

## VM demonstration (this lane, 2026-11-06)

This VM has no GPU and no RADV (no /sys/class/drm
devices, no amdgpu hwmon, no vulkaninfo), so the
trace-side artifacts cannot be produced here; what
was demonstrated is the wrapper machinery and the
sampler against dummy processes. Demo run directories
were removed after capture; the wrapper recreates
everything per run.

1. `bench/gpu-trace.sh vm-demo -- sleep 3` — exit 0
   preserved. telemetry.csv: 27 rows over the 3 s
   lifetime at ~10 Hz; RSS live (1,752 KiB, sleep);
   load live (2.20); VRAM/temp/power columns empty
   with header lines `# vram source: ABSENT (no
   amdgpu mem_info counters on this host)` and the
   hwmon equivalents. manifest.txt complete (command,
   child env, git SHA 2f8b3ae, Mesa "not readable on
   this host", inventory). rgp collected: 0; stats
   blocks: 0; asm/NO_ASM_FOUND.txt written; canary:
   ABSENT (neither vkpeak nor clpeak on PATH here).
2. RSS tracking: a python3 dummy that allocates and
   touches 200 MB, then sleeps 2 s. Peak
   proc_rss_kib in its telemetry.csv: 205,760 — the
   sampler follows the target process's growth.
3. Exit-code preservation:
   `bench/gpu-trace.sh vm-exit -- sh -c 'echo demo-out;
   echo demo-err >&2; exit 7'` returned exactly 7,
   with demo-out in stdout.log and demo-err in
   stderr.log.
4. Hang knob: `GPU_TRACE_HANG=1 bench/gpu-trace.sh
   vm-hang -- true` recorded
   `RADV_DEBUG=shaderstats,asm,cs,hang` in the
   manifest's child_env line.
5. INDEX.md gained exactly one line per demo run,
   in the documented format.

## Not verified locally (server run settles these)

- Whether Mesa 26.0.8's RADV writes per-submit .rgp
  files for headless compute at all, how many, and
  exactly where (CWD vs /tmp). The sweep covers both;
  a clean server run that collects zero .rgp files is
  itself the finding, and the follow-up would be the
  trigger knobs (MESA_VK_TRACE_TRIGGER /
  MESA_VK_TRACE_FRAME), not silent re-runs.
- The exact stderr spellings of the stats and
  disassembly headers on the server's Mesa. The
  extractors key on the autopsy's proven patterns
  plus a loose 'disassembly' key; stderr.log is filed
  raw either way, so a spelling miss loses nothing
  but the extraction, and the note for that run
  should record it.
- vkpeak/clpeak presence on ubuntu-server. The
  wrapper checks at run time; canary.txt is the
  record either way.
- shellcheck was not run: it is not installed on
  this VM (checked 2026-11-06). The script header
  carries the same note; run shellcheck on the
  server before the first traced session.

## First server run (to schedule)

One 1,022-token prefill_profile run under the wrapper,
from the staged tree (manifest-verified, as every
proof run), inside the phase lock, card cleared, the
Cortex tenants stopped before and restored after per
the restart sheet (~/card-clear-2026-11-05.md). This
is the natural first capture: prefill is the measured
problem (MMQ pair at 43.5 GB/s against GEMV's
649.5 GB/s in the same profile), and the RGP is the
tool the research prescribed for exactly those
kernels before any further redesign.

```sh
ssh -F /home/hatch/.ssh/ts/config ts-server
cd ~/gpu-wave<N>   # staged tree for the current main
flock -w 14400 /tmp/itak-phase.lock bash -c '
  set -u
  systemctl --user stop cortex-embed.service
  docker stop cortex-cortex-chat-1 cortex-cortex-embed-1
  # VRAM guard (prefill-profile-run.sh rule): the big
  # card must read at or under 500 MB used; cleared
  # state reads about 33 MB. Abort if not.
  used=$(cat /sys/class/drm/card2/device/mem_info_vram_used)
  echo "vram used before: $used"
  [ "$used" -le 500000000 ] || { echo "CARD NOT CLEAR"; exit 1; }
  export PATH="$HOME/.cargo/bin:$PATH"
  export CARGO_BUILD_JOBS=4 MALLOC_ARENA_MAX=2 MALLOC_TRIM_THRESHOLD_=0
  cargo build --release -p itak-loader --example prefill_profile
  sentence="The quick brown fox jumps over the lazy dog. "
  prompt_long=""
  for i in $(seq 1 102); do prompt_long="$prompt_long$sentence"; done
  WGPU_COMPUTE_DIAG=timing \
  WGPU_COMPUTE_DIAG_OUT="$PWD/gpu-trace-first-diag.csv" \
    bench/gpu-trace.sh prefill-1022 -- \
    target/release/examples/prefill_profile \
      /mnt/models/Muse-Glimmer-30B/Muse-Glimmer-30B-KQuant-17GB-Q4_K_M.gguf \
      "$prompt_long"
  echo "wrapper exit (prefill_profile exit): $?"
  docker start cortex-cortex-chat-1 cortex-cortex-embed-1
  systemctl --user start cortex-embed.service
'
```

(The card2 sysfs path is the one the 2026-11-05
sessions read on this host; if the enumeration moved,
read `mem_info_vram_used` from whichever card device
reports the 25.75 GB total.)

Acceptance for the run, checked in the run directory
under bench/traces/: wrapper exit 0; at least one .rgp
collected (or the zero-.rgp finding above recorded in
that session's note); shaderstats.txt block count
above zero; telemetry.csv rows spanning the run at
~10 Hz with VRAM, RSS, temperature, and power all
live; canary.txt holding a vkpeak (or clpeak) reading
or the recorded absence; the diag CSV populated
beside it. Open the .rgp in Radeon GPU Profiler and
read the MMQ kernels' occupancy, instruction timing,
and LDS bank conflicts before the K23/flash/coopmat
lanes draw conclusions the profile alone cannot
support.
