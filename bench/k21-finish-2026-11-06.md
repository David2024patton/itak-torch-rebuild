# K21F: the finish-carrying K21 variant for the Q5_K head (2026-11-06)

Lane `lane/k21-finish`, from main a064b5d7. New
kernel module
`crates/wgpu-compute/src/kernels/k21_q5k_mmv_finish.rs`
(pipeline `K21FinishPipeline`, call `K21FinishCall`,
diag stamp `k21_q5k_mmv_finish`), registered on the
backend as `WgpuCompute::k21_finish` and built
unconditionally at backend construction like its
siblings. NO session code routes to it in this
lane: the routing change is a separate lane, and
this note carries the protocol that earns it.
GPU-less VM gates only here; the card verdict is
sequenced below.

## Why this exists: the zero in the verdict

The 2026-11-06 server verdict on K21
(bench/mmv-q5k-2026-11-05.md) is the whole reason:
K21 is correct (card-executed against the CPU
reference and K3 at batches 2, 3, 5, 7, 9, 16, both
reduction shapes), compiled clean (zero spills,
zero scratch, LDS 1,024 B, VGPR 96 plateau), and
faster than the K3 GEMV at nearly every in-band
Q5_K row of the sweep harness. It also fired zero
times in 46,739 per-dispatch diag lines of the
flagged real resident runs, because on the
Muse-Glimmer-30B Q4_K_M file the Q5_K tensors in
the resident forward are the head, and the head
sites prepare K3 with a fused finish
(`prepare_with_finish`: logit scale, and the tanh
softcap when the file carries one) that plain K21
does not carry. The note named the follow-up in
its own text: "The head-sized prize needs a
finish-carrying K21 variant." This is that
variant, built to the evidence.

The prize is sized in bench/dflash-gpu-2026-11-03.md:
the borrowed Q5_K head is the single largest
stream in the DFlash pass (the head tensor is
about 0.86 GiB, read once per block row batch).
The site that can feed it is the BLOCK head: the
session prepares it at the chunk's full batch
(`rows`), which on the speculative paths is the
DFlash block width, inside this kernel's 2..=16
band. The standard head runs at batch 1, below the
band floor, and stays K3 by construction; nothing
in this variant pretends otherwise.

## The design

One structural variable against plain K21: the
finish at the store. One against K3: the workgroup
organization. The arithmetic is shared with both.

- The product generator mirrors K21's `mmv_shader`
  line for line (the crate's per-kernel generator
  idiom): same shape (`K21Shape`, K21's
  `shipped_shape`, imported, not re-typed), same
  per-batch generation literals and fully unrolled
  accumulators, same dequant and dot text (verified
  byte-identical against K21's generator literals
  for the dequant block, the dot block, and the
  reduction scaffolding during the build), same
  reduction orders in both shapes, same band
  (2..=16) with the same refusal text, same
  one-workgroup-array invariant (the reduction
  partials only). The half-conversion WGSL is
  K21's own constant bound by reference
  (`pub(crate)` widening in k21_q5k_mmv.rs, the
  only edit to that module), so the two generators
  cannot drift on it.
- The finish is K3's, whole: the `finish_apply`
  WGSL is K3's function text character for
  character (mode 1: `v * scale`; mode 2:
  `cap * tanh(scale * v / cap)`, K8's expressions
  in K8's order), the mode constants are K3's
  `FINISH_SCALE` / `FINISH_SOFTCAP` imported from
  k3_q5k_gemv (never redefined), and mode, scale,
  and cap travel as uniform words in the params
  tail exactly as K3's do (scale and cap as f32 bit
  patterns; word order pinned by a unit test,
  because a transposed tail compiles clean and
  only a wrong answer would show it). The finish
  is uniform state, not a generation literal, so
  the variant count stays K21's 15 per shape.
- The prepare surface is K3's signature verbatim:
  `prepare_with_finish(ctx, weights, input,
  output, batch, mode, scale, cap)`, so the head
  site can swap product engines without changing
  what it asks for. Validation is K3's, with K3's
  refusal words: a non-finishing or unknown mode
  refuses ("finish mode {mode} is not a finishing
  mode"), a softcap with a non-positive cap
  refuses ("softcap {cap} is not positive"). The
  band and buffer checks are K21's, with K21's
  words. Validation is factored into a free
  function and the params packing into another, so
  both are unit-tested on a GPU-less machine.
- Dispatch count is 1, the same as K3's fused head
  dispatch and K21's own: routing the block head
  here changes the product engine, not the plan's
  dispatch accounting, and no K8 finish dispatch
  appears or disappears (the Q5_K head never paid
  one; its `finish` slot in the plan is `None`
  today and stays `None`).
- Diag instrumentation from birth (David's rule):
  prepare stamps `k21_q5k_mmv_finish` through
  `ctx.diag_stamp` with rows, cols, quant `Q5_K`,
  weight bytes, and a `batch=<n> finish=<mode>
  grid=<x>x<y>` shape string (K3's stamp
  convention for the finish field, under this
  kernel's own name so the timing table separates
  it from both plain K21 and K3).
- Env gating: none of its own, consistent with
  the family. When routing lands, it rides the
  shared `WGPU_COMPUTE_MMV_MAX_ROWS` threshold
  like K19, K20, and K21; the shipped default
  stays governed by the K19 verdict (off).

## The math-equivalence argument

Claim: for any input the head site can present,
this kernel's output equals the shipped head
composition's output (K3 product + K3's fused
finish) inside the family's reassociation bound,
shrunk by the finish. Three steps.

1. Same product math. The dequant and dot text is
   K3's verbatim in both K21 and this variant
   (K21 is a proven port of the same mul_mat_vec
   family), and the reduction sums the same
   per-thread partials in the same orders per
   shape. The raw sums therefore differ only by
   f32 reassociation, the bound the family is
   already gated on: card-measured for K21 against
   both the CPU reference and K3 at 2.0e-3 to
   2.9e-3 absolute on fixture set scales of 1.8e4
   to 3.3e4 (bench/mmv-q5k-2026-11-05.md, step 1).
   This variant changes nothing under the sum.
2. Same finish, same position. The finishing map
   is a pure elementwise function of the fully
   reduced sum. K3 applies it at the reduction's
   final store, the only store of each element;
   this kernel applies the identical function at
   the identical position in both reduction
   shapes. There is no intermediate buffer, no
   second pass, and no other writer of the output
   elements in either kernel, so no ordering or
   rounding difference can enter between the sum
   and the map.
3. The map contracts differences. Both modes are
   Lipschitz with constant `scale`: mode 1
   multiplies by `scale` exactly; mode 2's
   derivative is `scale * sech^2(scale * v / cap)`,
   at most `scale`. So |finish(a) - finish(b)| is
   at most `scale * |a - b|`, and at Glimmer's
   logit scale (0.19611613) the finished outputs
   agree to about a fifth of the raw bound. The
   one evaluation that is not shared arithmetic,
   `tanh`, is the driver's WGSL `tanh` in both
   kernels on the same device, so even it is the
   same evaluation in the production comparison;
   the test bound still carries a 2e-5 absolute
   slack for it against the host-composed
   reference, where the host's f32 `tanh` is a
   different implementation.

The unavoidable difference, stated plainly: none
in the finish itself. The only difference from
the shipped head is the one K21 already carries
against K3, f32 reassociation in the product,
bounded in step 1 and shrunk in step 3. If a
future driver compiled this shader's accumulators
into spills, that would be a performance
difference, not a math one; step 0 of the
protocol below checks the compiled form before
any timing is read.

Inherited parity, not a new decision: like K3,
the prepare does not validate `scale` (any f32
passes to the uniform) and a NaN softcap cap is
not caught by the `cap <= 0.0` check (NaN compares
false). Both behaviors are the shipped head's;
this variant matches them rather than quietly
diverging, and any change belongs to a lane that
changes both kernels together.

## The routing change this hands to the next lane

Specified here so the integration is mechanical;
NOT done in this lane (session.rs is untouched).

1. A `ProjCall::MmvQ5KFinish(K21FinishCall)`
   variant: encode_into delegates to the call;
   `kernel_name()` returns `k21_q5k_mmv_finish`;
   `dispatches()` is 1; `quantized()` is false
   (the form consumes f32 rows, like the other MMV
   arms).
2. A `try_mmv_q5k_finish(backend, weights, input,
   output, batch, mode, scale, cap)` beside
   `try_mmv_q5k`, gated on `mmv_applies(backend,
   batch)`, preparing through
   `backend.k21_finish().prepare_with_finish(...)`,
   logging any refusal by name and returning None
   (the ladder continues to K3, whose call the
   head site builds today).
3. At the BLOCK head site only (the Q5_K branch
   that today calls
   `backend.k3().prepare_with_finish(...)` at
   `rows`): try the finish form first when the
   band applies, fall back to the existing K3 call
   on None. The standard head site (batch 1) is
   not touched: the band refuses it by
   construction, and decode stays K3's.
4. Dispatch accounting does not move: both forms
   are one dispatch with the finish fused, and the
   site's `finish` slot stays `None` on both
   paths.
5. `K21FinishPipeline::precompile` at the block
   batches the session will run, at plan time, as
   the family does for K21.

## Server verdict protocol (the next lane)

Preconditions: the card cleared per David's
standing order (he clears Cortex tenants for test
sessions; production Glimmer stays down); the
phase lock `flock /tmp/itak-phase.lock` held; one
heavy job at a time; the staging tree synced to
the merged commit and its hash verified before
any run; `WGPU_COMPUTE_MMV_MAX_ROWS` unset for
every control.

0. Shader autopsy of the compiled finish variants,
   before any timing: extend the
   bench/shader-autopsy.sh pattern to the
   K21Finish pipelines at batches 2, 7, and 16 and
   record VGPR, SGPR, spills, scratch, and LDS per
   variant, against plain K21's recorded form
   (zero spills, zero scratch, LDS 1,024 B, VGPR
   84 at batch 2 rising to the 96 plateau). The
   claims to check: the finish (a multiply, and a
   tanh in softcap mode, at the store only) adds
   no spills and no scratch, and LDS stays the
   partials size. A spill the finish introduces
   would be a finding against the fusion, priced
   before any speed number is believed.
1. Correctness gates execute (no skips) on the
   card:
   `cargo test -p wgpu-compute --test k21_finish -- --nocapture`
   (batches 2, 3, 5, 7, 9, 16 against the CPU
   composition and against K3's fused finish, both
   reduction shapes, both finish modes at
   Glimmer's real scale and softcap; the 768 x 101
   deep geometry; the head's own 6,656 width; the
   named refusals) and the compile leg:
   `cargo test -p wgpu-compute --test shader_compile k21_finish`
   (all 15 batch variants, both shapes). Record
   the max abs diffs the file prints: the argument
   above predicts them at or below about a fifth
   of K21's recorded raw diffs (2.0e-3 to 2.9e-3)
   at the same fixtures, i.e. roughly 6e-4 or
   under; a larger finished diff contradicts the
   Lipschitz step and stops the protocol until it
   is explained.
2. Exposure check FIRST, before any speed reading,
   in a real resident run (this requires the
   routing change above to be in the staged tree):
   with `WGPU_COMPUTE_MMV_MAX_ROWS=16` and
   `WGPU_COMPUTE_DIAG=timing`, run itak-spec's
   `spec_generate_gpu` against the real target and
   draft files at depth 6 and depth 1, greedy,
   Stage 1 prompt. Read the per-dispatch diag lines
   in the run log (NOT the `WGPU_COMPUTE_DIAG_OUT`
   CSV: the 2026-11-06 verdict recorded that
   successive session reports overwrite it, and the
   surviving file can be the wrong session's).
   Require: `k21_q5k_mmv_finish` lines present,
   stamped `finish=2` (Glimmer's softcap position),
   at the block batches the run executes; the
   head's `k3_q5k_gemv` lines reduced to the
   standard head's batch-1 calls only. Zero
   `k21_q5k_mmv_finish` lines means the routing did
   not land or the band did not open; stop there
   and say so, as the K21 verdict did.
3. Identity + golden with the finish form routed:
   the same runs as step 2 must print IDENTITY and
   GOLDEN PASS in the on position before any speed
   number is read. Control: the same runs with the
   variable unset (the head entirely on K3, as
   shipped; identity and golden must pass there
   too, and the diag table must show zero
   `k21_q5k_mmv_finish` lines, proving the off
   position is the shipped composition exactly).
4. Head-heavy timing comparison: the DFlash pass
   is the head-heavy surface (the head is its
   largest single stream). From the step 2/3 runs'
   diag tables, compare the head's per-dispatch
   totals: `k21_q5k_mmv_finish` against the
   control's block-head `k3_q5k_gemv` rows (same
   batches, same tensor), and report end-to-end
   effective tok/s and acceptance at depths 6 and
   1 for both arms, against the recorded baselines
   (depth 6 control 9.09 to 9.21 tok/s, depth 1
   control 14.22 to 16.98 tok/s, from the K19/K21
   verdict sessions). Acceptance must be identical
   per depth across arms (the finish form changes
   no math beyond the bound in step 1 of the
   argument); an acceptance change is a correctness
   finding, not a speed result. Plain decode is
   batch 1 and cannot route here; its rate must
   read unchanged (35.45 tok/s class) in both arms
   as the no-leak check, as in the family's earlier
   protocols.

Decision rule: the routing stays behind the
shared MMV threshold, whose default is governed
by the K19 verdict and does not move on this
variant's evidence alone. This variant's own gate
is narrower: it earns its routing when steps 0
and 1 are clean AND step 2 shows it firing at the
block head in the real forward AND step 3 passes
identity and golden in the on position AND step 4
shows the head's diag time no worse than K3's at
the same batches. Anything less, the block head
keeps preparing K3 and the table is recorded here
as the finding.

## The routing (lane/k21f-routing, 2026-11-06)

Landed as specified above, in commit d0ebbd9 on
`lane/k21f-routing` (from lane/k21-finish
b4f6549). What routes where:

- The BLOCK head site only (`ChunkPlan::build`'s
  Q5_K branch, prepared at the chunk's full batch
  `rows`): `try_mmv_q5k_finish` (beside
  `try_mmv_q5k` in session.rs) runs first, gated
  on `mmv_applies` (the shared
  `WGPU_COMPUTE_MMV_MAX_ROWS` threshold; shipped
  default 1 = closed). On `Some`, the plan's
  block head is `ProjCall::MmvQ5KFinish`
  (encode delegates to the call, diag name
  `k21_q5k_mmv_finish`, dispatches 1,
  `quantized()` false). On `None` the site
  prepares the K3 fused call it built before this
  lane, unchanged.
- The fallback rule: every refusal path returns
  `None` and falls back: gate closed (batch under
  2 or past the resolved threshold), the kernel
  band's own refusal at prepare (batch past 16,
  geometry), and the finish validation's refusal
  (non-finishing mode, non-positive softcap cap),
  the prepare refusal logged by name on the diag
  channel ("mmv q5k finish refused at the product
  prepare: ...; the k3 fused form serves it").
  The fallback K3 call is asked for exactly what
  the finish form was asked for (same mode
  derivation from `cfg.logit_softcap`, same
  `cfg.logit_scale` and `cfg.logit_softcap`
  expressions), so the site's finish request is
  identical on both paths; only the product
  engine changes. Nothing in the routing touches
  the finish's order or drops an element: the
  mode, scale, and cap travel as the prepare's
  arguments verbatim on both paths, and the
  finish itself is K3's function at the same
  store position inside K21F (the build lane's
  argument above; nothing in this lane re-opens
  it).
- The standard head site is untouched: it
  prepares K3 at batch 1, and batch 1 never
  passes the gate at any threshold (pinned), so
  decode stays K3's by construction. The draft
  session is untouched (its head is a plain
  projection and already routes through the
  plain ladder). Dispatch accounting does not
  move: the routed form is one dispatch with the
  finish fused, and the site's `finish` slot
  stays `None` on both paths.
- The registration's `#[allow(dead_code)]`
  markers on the backend field and accessor are
  lifted, as the build lane instructed: the
  accessor has its first reader. The band
  arithmetic is factored into the pure
  `mmv_band_admits(max_rows, batch)` helper
  (`mmv_applies` delegates to it) so the gate is
  unit-pinnable without a device.

Two readings of the spec, recorded honestly:

- Step 5 of the hand-off (a
  `K21FinishPipeline::precompile` at plan time
  "as the family does for K21") has no separate
  call, here or anywhere in the session: no
  session code calls `precompile` for any MMV
  family member in this tree. The family's
  actual mechanism is that `prepare` compiles
  the batch variant on first use, and every
  prepare in `ChunkPlan::build` happens at plan
  build, before any forward runs, so the block
  batches' finish variants compile at plan time
  by the same construction K21's do. Adding a
  redundant precompile call would only duplicate
  the cache lookup; none was added.
- The kernel module's doc header still reads
  "no session code prepares this pipeline yet":
  kernel files were out of this lane's scope, so
  the line is stale as of this commit and is
  flagged here for whichever lane next touches
  that module.

Tests added with the routing: two unit pins in
session.rs (`mmv_band_never_admits_batch_one_
so_the_batch_one_head_stays_k3`,
`mmv_band_admits_the_block_batch_only_when_the_
gate_is_open`) and `tests/k21f_head_routing.rs`,
