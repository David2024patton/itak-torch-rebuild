# K22 Q4_K MMQ occupancy prototype (2026-11-05)

Lane: lane/k22-mmq, from main 060546b. Status: built and
gated on the VM; NOT measured on the card. The server
verdict protocol is at the bottom. The kernel ships
behind `WGPU_COMPUTE_K22_MMQ=1`, default OFF; at shipped
defaults the session ladder is byte-identical to the
ladder every prior proof ran on.

## The problem, from the measurements

Prefill profile (bench/prefill-profile-2026-11-05.md,
cleared RX 7900 XTX, real Glimmer Q4_K_M, 1,022 tokens):

| kernel | count | total_ms | share | GB/s | % FP32 peak |
|---|---|---|---|---|---|
| k13_q4k_mmq | 2,912 | 4,199.9 | 63.1% | 46.4 | 17.2% |
| k14_q6k_mmq | 832 | 1,342.0 | 20.2% | 34.6 | 8.8% |
| k3_q5k_gemv (lm_head) | 16 | 22.8 | 0.3% | 649.5 | 3.1% |

Shader autopsy (bench/shader-autopsy-2026-11-04.md):
K13 compiles to VGPR 256, the architectural per-wave
maximum, zero spills, LDS 41,984 B reported. Occupancy
per CU is at the floor, which costs latency hiding; the
GEMV control case in the same run proves the memory
system can stream at ~650 GB/s. Verdict in the profile's
own words: neither stream-bound nor compute-bound;
occupancy/instruction bound. The fix must live inside
the kernel: fewer live values per thread.

## What K22 is

K13's exact math and contracts, llama.cpp `mul_mmq`'s
register organization:

- Same staged values, same K12 Q8_1 input layout, same
  bindings, same params, same `[batch][out]` output, so
  the session swaps forms without moving a byte. The
  prepare contract is K13's (batch 1..=64, same named
  refusals).
- Tile coverage unchanged: 64 output rows x 64 batch
  rows per workgroup, same dispatch grid as K13 m64.
- 128 threads instead of 256. Warp tiling mirrors
  llama: four warps, each on a 16-output-row x 64-batch
  warp tile. Per thread: 4 output rows x 8 batch rows =
  32 f32 accumulators.
- Per 32-element sub-block, the thread loads its four
  rows' operands into a named register cache (8 packed
  words + the `(d*scale, dmin*min)` pair per row), then
  walks its eight batch columns one at a time: load the
  column's 8 words + `(d, s)` pair, run four scalar i32
  dots (8 DP4A each), fold each into its accumulator
  immediately. No `isum` array, no fold phase.
- One staging change: the weight tile's row stride is
  padded 64 -> 65 words, the skew K13 already applies
  to its activation tile. K22's mapping puts four
  distinct output rows on one wavefront load instruction
  (K13's puts two); at a 64-word stride those addresses
  share one LDS bank. Staging total 41,472 B (K13 m64:
  41,216 B; the +256 B is exactly the padding).

## Register arithmetic

Source-level live values at the inner peak. K13's row is
read off its generated shader text; its compiled result
is the autopsy's measured 256.

K13 (per generated sub-block scope, unrolled x8 with no
barrier between sub-blocks):

| live set | values |
|---|---|
| f32 accumulators `acc[16]` | 16 |
| i32 `isum[16]`, live across all 8 word steps | 16 |
| operand lets per word step (4 weight + 4 activation words) | 8 |
| fold pairs `c[4]` + `dm[4]` (vec2) | 16 |
| row/col indices, staging and address state | ~15-25 |
| named peak | ~75-85 |

The gap between ~80 named and 256 compiled is the
scheduler's freedom: the eight unrolled sub-blocks are
independent until their folds, so latency hiding rewards
keeping several sub-blocks' operand windows (and their
staging address chains) in flight at once. The autopsy
cannot attribute the 256 more precisely from outside;
what it proves is that the compiled form, not the
algorithm, is the cost.

K22 (per generated sub-block scope):

| live set | values |
|---|---|
| f32 accumulators `acc[32]` | 32 |
| register cache: 4 rows x (8 words + vec2 pair) | 40 |
| column operand: 8 words + vec2 pair | 10 |
| scalar dot accumulators in flight (one per row) | 4 |
| row/col index lets, live across the K loop | 12 |
| loop/address state | ~6 |
| named peak | ~104 |

Expected compiled band: 96-128 VGPR. Even if the
scheduler hoists one full sub-block of cache loads
(+40), it lands near 140, still off the cap. At 128
VGPR, resident waves per SIMD double versus the
256-VGPR floor. This is a prediction with its arithmetic
shown; step 0 of the verdict protocol measures it, and
the prototype's claim stands or falls there.

LDS traffic per DP4A also improves on paper: K13 reads
64 operand words per thread per sub-block for 128 dots
(0.50 reads/dot); K22 reads 96 for 256 dots (0.375),
because the A-side cache is reused across 8 columns
instead of 4. The DP4A count is identical (2,048 per
thread per super-block at K22's 32 outputs; 262,144 per
workgroup per super-block either way).

## Deliberately not copied from llama's mul_mmq

- **Its Q4_K staging repack.** llama interleaves two
  16-element halves into each staged word
  (`vals0 | vals1 << 4`) and permutes the activation
  order to match, extracting nibbles by shifts inside
  the dot. That halves the register cache's words per
  row entry (4 vs K22's 8; llama's whole cache_a is 48
  values to K22's 40 for half the rows). Not copied
  because it changes the staged byte layout and the
  B-side element order: a second design variable and a
  new correctness surface, in a prototype whose single
  variable is register organization. It is the named
  follow-up if K22's organization wins but its cache
  still costs too much.
- **The coopmat (WMMA) form.** The profile note ranks
  it below the plain rework: same 650 GB/s streaming
  ceiling, more risk, a second code path.
- **Load width 4 in `mm_load_vec_a`** (the mul_mm f32
  path's staging width). K22 stages from DRAM exactly
  as K13 does (the staging loops are K13's, with the
  one stride change); the A-operand width that matters
  for the register question is the LDS-to-register
  cache load, which is word-granular in both K13 and
  K22.

## Routing

`mmq_product_q4k` in session.rs: wide (K15) first past
its threshold, then K22 when `backend.k22_mmq()` is on
and its pipeline exists, then K13. A K22 prepare refusal
is logged by name and K13 serves the projection, the
ladder's standing rule. The switch is resolved at
backend construction from `WGPU_COMPUTE_K22_MMQ`; only
the exact value `1` enables it (fail-closed, unit-tested).
The pipeline itself is built at construction regardless,
so a shader defect fails there, not on first routed use.

## Server verdict protocol

Preconditions: card cleared per David's order, phase
lock held, staging synced to the lane commit and
hash-verified, the prefill profile harness
(`prefill_profile`, from lane/prefill-profile) available
for step 3.

0. **Shader autopsy first.** Compile K22 in isolation
   (the shader_compile leg) under
   `RADV_DEBUG=shaderstats,asm,cs` with a private
   `MESA_SHADER_CACHE_DIR`. Read VGPR, spilled VGPR,
   scratch, LDS. The prototype's premise is the VGPR
   line: if it reads 256 (or spills), the organization
   failed in compiled form and steps 1-3 are moot;
   stop and report.
1. **Correctness on the card.** `cargo test -p
   wgpu-compute --test k22_mmq` must actually execute
   (not skip): reference and K13 parity at batches 16,
   32, 64 and the 62-row tail, plus the band refusals.
   Also `resident_session` with `WGPU_COMPUTE_K22_MMQ=1`:
   identity + golden on the real file before any speed
   number is read (the dispatch-count pins will move by
   design under the env; the token checks are the gate).
2. **Kernel-level A/B.** The `mmv_sweep`-style per-tensor
   bench is small-batch; for the MMQ band use the
   profile harness: same 1,022-token prompt, diag timing
   on, K22 env on vs off. Compare the `k22_q4k_mmq` row
   against K13's recorded 4,199.9 ms / 46.4 GB/s and the
   total GPU time against 6,659 ms. Report the achieved
   GB/s and % of FP32 peak beside K13's.
3. **Prefill A/B, session level.** `glimmer_generate
   --gpu` wall on the same prompt, env on vs off, three
   runs each, timing-off walls compared (the profile's
   off wall was 8,116-8,169 ms).
4. **No-leak check.** With the env unset, plain decode
   and the spec verdict harness must reproduce their
   recorded numbers (decode 35.45 tok/s class); K22 is
   unreachable with the switch off, so any movement is a
   routing leak, not a kernel result.

Decision rule: the switch's default stays OFF unless
step 0 shows VGPR off the 256 cap with zero spills AND
step 1 passes in full AND step 2 shows the Q4_K MMQ
line materially faster (a wash inside run-to-run noise
is not a win; the profile's two runs agreed to 0.5%).
Any default flip is a separate change with this note's
numbers attached, and the Q6_K sibling (K14, same
disease at 20.2% of GPU time) gets its own prototype
before the pair is called fixed.

## What could still make K22 lose to K13 on the card

Honest list, in the order I would bet on them:

1. **ACO ignores the source organization anyway.** The
   scheduler may hoist and interleave K22's sub-blocks
   just as it does K13's and land at or near 256 VGPR.
   The braced scopes bound live ranges in the source,
   but nothing in WGSL forces an allocation. Step 0
   exists precisely to answer this cheaply.
2. **The 256-thread workgroup was hiding something.**
   K22 halves the threads per tile; if K13's rate was
   partly thread-parallelism over the staging loops
   (256 threads stage the same bytes in half the
   passes), K22's staging phase per super-block round
   runs longer, and at 52 layers x 26 columns that adds
   up inside the same barrier structure.
3. **LDS read pattern.** K22's cache loads are
   broadcast-friendly by construction, but its B-side
   reads stride across the skewed activation tile in
   (wsic, cc) order; a bank pattern I got wrong costs
   ds_load throughput on every one of the 96 reads per
   sub-block. The 4-way weight-side conflict the skew
   fixes could also reappear through the vec2 pair
   arrays (8-byte elements pair lanes differently).
4. **The fold is more frequent per accumulator.**
   K22 folds 32 times per sub-block per thread (once
   per (row, column)) where K13 folds 16; the fold's
   f32 ops per output are the same, but K22's are
   interleaved with the dots, lengthening the dependency
   chain each accumulator waits on if the scheduler
   cannot find independent work inside one thread.
   Occupancy is supposed to cover exactly this; if it
   does not, the chain shows.
5. **Instruction count.** Same DP4A count, but K22
   issues more LDS load instructions per super-block
   per thread (768 word loads vs K13's 512) and more
   address arithmetic for the cache indexing. At 17%
   of FP32 peak the kernel is not dot-throughput-bound,
   but it could be issue-bound in a way the profile
   cannot distinguish from occupancy.
