# Coopmat v2 (K24): autopsy of v1, the register-resident rebuild, and the card protocol owed

Date: 2026-11-07. Lane: lane/coopmat-v2, from main
0ecdc8ff5efc3da0d00b5806c8f2796b65096132. VM work only;
no server GPU jobs were run for this lane. The card
verdict is owed under the protocol at the end.

State of the art this builds on: the coopmat bridge
works and is numerically transparent
(bench/coopmat-build-2026-11-06.md,
bench/defaults-confirmation-2026-11-07.md). The v1
kernel (K23, stamp k23_q4k_coopmat) is correct
everywhere and 4.0x slower than K13 at the kernel
line: 16,951.3 ms / 11.5 GB/s against K13's
4,250.1 ms / 45.9 GB/s over 2,912 dispatches at the
1,022-token prefill shape; wall 19,851 ms against
7,164 ms. The routing flag WGPU_COMPUTE_COOPMAT
stays off. This note is the v2 build record: the
autopsy first, then what v2 changed, then the exact
card protocol that judges it.

## The autopsy: v1 against llama's mul_mmq_cm1

Sources read in full for this diff: our
crates/wgpu-compute/src/kernels/coopmat/k23_q4k_coopmat.comp;
llama.cpp's ggml/src/ggml-vulkan/vulkan-shaders/
mul_mmq_cm1.comp and mul_mmq_cm1_funcs.glsl (VM
mirror, sha256-identical to the server tree of the
a7af149 lineage); ggml-vulkan.cpp's cm1 enablement
and warptile construction; Mesa's
src/amd/vulkan/nir/radv_nir_lower_cooperative_matrix.c
(the RADV lowering that defines the fragment layouts
on the target driver).

### Structural diff, axis by axis

**Cooperative-matrix tile shape and tiles per
subgroup.** Same 16x16x16 s8 x s8 to s32 tiles (the
only shape the card's property rows offer). Per
subgroup the warp tile differs in size, not shape:
llama's large class runs BM 128 x BN 128 with
WM 32 x WN 32 warp tiles at wave32 (16 subgroups of
32 in a 512-thread workgroup, cms_per_row =
cms_per_col = 2, CM_ELEMS 8, 32 f32 sums per thread).
v1 runs 128 x 64 with WM 64 x WN 32 at wave64 (4
subgroups of 64 in a 256-thread workgroup,
cms_per_row 4, cms_per_col 2, 32 f32 sums per
thread under its slice mapping). The batch side is
capped at 64 by this backend's MMQ band contract
(K13's MMQ_MAX_BATCH), so the 128-wide batch tile is
not available to either of our kernels; that is a
contract difference, not a craft difference.

**Subgroup width (the axis v1's build note did not
name).** llama runs cm1 on AMD at wave32:
ggml-vulkan.cpp computes cm1_use_wave32 (vendor AMD,
subgroup size control present, range covering 32)
and builds the pipeline requiring a 32-wide
subgroup, with WARP set to 32, so USE_MAGIC_BIAS is
false on this stack. Our stack cannot do that: the
passthrough path hands wgpu a shader module and
wgpu creates the pipeline; there is no
required-subgroup-size control through it, so our
kernels run at the device subgroup size the bridge
probes, 64, and K23's constructor requires exactly
that. Every wave-dependent choice in v2 is made for
wave64 on purpose, below.

**Weight staging.** Identical in structure: llama's
split layout transcribed in v1 (raw nibble codes at
QPITCH 36 with the +4 bank skew, (d*scale,
-(dmin*min)) vec2 pairs in a separate array). One
real difference: llama splits staging into a
PREFETCH_BLOCK (global loads into registers) and a
STORE_BLOCK_TO_LDS, prefetching the next chunk
while the current one computes. v1 loads global to
LDS directly per chunk, behind barriers. The B-side
x4 de-interleave repack in mul_mmq_funcs.glsl
belongs to llama's scalar MMQ path and its packed
input layout; our K12 output is already flat, and
v1's activation staging already mirrors the cm1
layout, so there is no repack gap on the coopmat
path.

**Activation staging and quantize path.** Identical:
K12's Q8_1 words staged flat, (d, d*sum) split into
two float arrays, the sum pre-scaled by d under the
same convention ggml's MMQ quantizer uses.

**The product loop (where the kernels actually
differ).** Per 32-element sub-block:
- Fragment loads: v1 loads fragments inside the
  (r, c, h) nest, 32 coopMatLoads: the A fragment
  reloaded once per column tile (x2), the B
  fragment once per row tile (x4). llama preloads
  register arrays once per sub-block (its Q4_K
  branch comment: "Preload all A/B fragments up
  front (ILP)"), 12 loads, reused across all tiles.
- The fold: v1 stores every finished 16x16 int tile
  to a shared fold tile (coopMatStore), subgroup
  barrier, scalar fold by the half of the subgroup
  whose columns fall in the tile, subgroup barrier:
  per staged chunk (4 sub-blocks x 8 tiles) that is
  32 coopMatStores and 64 subgroup barriers, with
  the matrix units serialized behind scalar LDS
  folds. llama folds in-register: it reads acc[e]
  directly and applies cm1_accumulate per element,
  with the element's row given by cm_elem_row and
  its column fixed per thread. Zero coopMatStores,
  zero barriers in the compute phase.
- Scale reads: v1 re-reads the weight scale pair
  per folded element out of the fold loop; llama
  reads scale_a/ma once per (r, e) and scale_b/bs
  once per (c) into registers. A consequence of the
  fold form, not a separate cause.

**Occupancy limiters.** v1 stages 37,888 B of LDS,
which caps it at 1 workgroup per CU on RDNA3's
64 KB LDS, and its grid at the wide prefill shapes
is 52 workgroups (out 6656 / 128) against K13
m64's 104, on a 96-CU card: 44 CUs idle and no
second workgroup anywhere to hide latency. No ACO
shaderstats for v1 were ever captured (the build
note records VGPR/spill data only for the WGSL
kernels); from the source's resource shape, v1's
per-thread state is small (32 f32 sums, few
indices), so LDS, not VGPR, is its occupancy cap.
llama's cm1 large class runs 512-thread workgroups
over a 128 x 128 tile: at out 6656 and batch 128
that is 52 x 8 = 416 workgroups. Our batch cap
makes that grid unreachable regardless of kernel
craft.

### Ranked causes

1. **The LDS fold in the inner loop.** 32
   coopMatStores plus 64 subgroup barriers per
   128-element chunk, each tile's product waiting on
   a scalar fold performed by half a subgroup while
   the other half idles. This is the only per-tile
   synchronous LDS round-trip in either kernel, it
   sits on the critical path of every sub-block, and
   it was the v1 build note's own first-named
   suspect ("the element-extraction epilogue in
   llama's cm_elem_row form"). Evidence: v1 source;
   llama's fold is register-only.
2. **Fragment reload multiplication.** 32
   coopMatLoads per sub-block against llama's 12,
   each an LDS cooperative load issued between
   muladds instead of once up front. The A-side
   reload factor is 2 (per column tile), the B-side
   4 (per row tile). Evidence: v1's loop nest
   against llama's cache_a/cache_b preload.
3. **Occupancy and grid (context, not the design
   target).** 37,888 B LDS pins 1 workgroup per CU
   and the grid is half of K13's at the wide shapes,
   so nothing hides the latency of causes 1 and 2.
   Deleting the fold tile returns only 4,096 B
   (33,792 B still exceeds the 32 KB that a second
   workgroup per CU would need), so this cause is
   recorded, not chased: v2 removes the latency
   itself instead of trying to hide it.

## What v2 changes (one design story)

K24 (stamp k24_q4k_coopmat; module
crates/wgpu-compute/src/kernels/k24_q4k_coopmat.rs;
shader crates/wgpu-compute/src/kernels/coopmat/
k24_q4k_coopmat.comp): the product loop stops
round-tripping through LDS; fragments and folds
live in registers.

- **Fragment preload.** Per sub-block, cache_a[4*2]
  and cache_b[2*2] register arrays loaded once with
  v1's exact coopMatLoad expressions, then reused
  for every (r, c) tile: 12 loads per sub-block.
- **In-register fold.** Per (r, c): the accumulator
  is built from the cached fragments and folded
  element by element with llama's cm1_accumulate
  identity in its plain (non-magic-bias) shape,
  sums[tile_idx * CM_ELEMS + e] in llama's indexing.
  buf_tile, every coopMatStore, and every
  subgroupBarrier are deleted; the workgroup
  barriers around staging are the only barriers
  left. The final store is llama's per-element
  guarded form.
- **The element mapping, and its evidence.** The
  fold reads acc[e] as tile element (row, col) with
  col = inv % 16 and row = (inv / 16) + 4e,
  CM_ELEMS = 4. This is Mesa's GFX11 wave64
  accumulator layout, read out of
  radv_nir_lower_cooperative_matrix: its load, store,
  and element-coordinate lowerings compute
  base_row = inv / 16 (radv_get_base_row),
  row_iter = e * wave_size / 16 = 4e at wave64,
  inner_idx = inv & 15, and the accumulator length
  16*16/64 = 4. The same formulas at wave32 give
  row (inv/16) + 2e and 8 elements, which is exactly
  llama's cm_elem_row, cross-validating the method
  against an independent implementation. llama's
  formula transcribed blindly would have been wrong
  here precisely because llama runs wave32 and this
  stack runs wave64 (see the autopsy). The mapping
  is a GFX11 layout; GFX11.5/12 take a different
  branch of the Mesa lowering and are out of scope,
  as they are for K23. The card numeric gate below
  is the proof on the target card: a wrong mapping
  scrambles rows and columns and fails by a wide
  margin, not by noise.

### Deliberately not changed

- Staging layout, loaders, QPITCH 36, the (d*scale,
  -(dmin*min)) and (d, d*sum) split arrays: byte for
  byte v1's transcription of llama's.
- Tile geometry: 128 x 64 workgroup tile, four
  subgroups of 64 owning 64 x 32, BK 32 in BK_STEP 4
  chunks, 256 threads. Same grid math (52 x 1 at
  out 6656, batch 64).
- The accumulate identity and its term order (the
  fma form is llama's expression shape; reassociation
  noise stays inside the MMQ check_close band the
  K13 parity gate uses).
- Magic bias: not adopted. llama's AMD
  configuration does not use it (WARP 32 makes
  USE_MAGIC_BIAS false), and at wave64 the plain
  path's float(acc[e]) conversion is exact for this
  kernel's dots (bounded by 32 * 15 * 127 = 60,960,
  far inside f32's exact-integer range).
- Staging prefetch split (llama's PREFETCH_BLOCK):
  a staging-side change and a different design
  story. Recorded here as the next step if the card
  convicts staging after the product loop is fixed.
- The buffer contract, the shape contract, and the
  call shape: K24's prepare/run are K23's, so plans
  swap forms without moving a byte.

### Routing

Behind the existing pair of switches, both
fail-closed exact-"1", resolved at backend
construction in compute.rs: WGPU_COMPUTE_COOPMAT
(the routing switch, unchanged) arms the coopmat
rung; WGPU_COMPUTE_COOPMAT_V2 (new) selects K24
over K23 inside that rung. Selector on but pipeline
absent, or K24 prepare refusing: the refusal is
logged by name and the v1 form serves, then the
standard ladder, exactly the rung's existing
fallback discipline. Both resolved values are named
in both sessions' diag manifests (coopmat,
coopmat_v2 pairs beside k21f_head). At shipped
defaults (both unset) nothing changes: the coopmat
rung is out of the ladder and K13 serves.

### Build and VM gates

- The shader was compiled on this VM with glslang
  16.6.0 (official Khronos release binary). Before
  trusting it, the same binary recompiled v1's
  checked-in shader to a byte-identical artifact
  against the server-produced original, so the
  toolchain is proven equivalent on this exact
  shader family. spirv-val (SPIRV-Tools 2025.1)
  passes on the v2 artifact (22,392 B).
- The disassembly (checked in beside the artifact)
  shows the structural claim at the binary level:
  OpTypeCooperativeMatrixKHR, OpCooperativeMatrixLoadKHR,
  and OpCooperativeMatrixMulAddKHR present;
  OpCooperativeMatrixStoreKHR absent (0 occurrences).
  Its workgroup variables are exactly the five
  staging arrays (uint[4608], vec2[512], uint[2304],
  float[256], float[256] = 33,792 B), matching the
  Rust constructor's STAGING_BYTES, which a unit
  test re-derives.
- rebuild-k24.sh sits beside rebuild.sh and asserts
  the same inventory (store absent) after a rebuild.
- Unit tests (VM): shape contract and grid math
  (K23's pins), the staging-bytes derivation, the
  artifact instruction walk (coopmat ops present,
  store count exactly 0), shader-text pins for the
  v2 structure (preload array declarations and
  sizes, the wave64 cm_elem_row formula, CM_ELEMS,
  QPITCH and the staging array declarations, the
  sums indexing, and the absence of buf_tile,

- Gate tallies (this lane tree, after the final

  integration targets k23_coopmat 3 passed and

## The card protocol owed

Run on ubuntu-server (RX 7900 XTX, RADV Mesa
26.0.8), staging synced to the merged commit and
the staged hash verified, tenants cleared under
the standing card rule and restored after, every
run wrapped in bench/failure-bundle.sh. Decision
rule, stated up front: K24 earns a default-flip
proposal only on a material kernel-line win over
K13 with speculative identity intact; otherwise
the selector stays off and K24 joins K23 as a
measured reference.

1. **Numeric gates first** (they are also the
   element-mapping proof): WGPU_COMPUTE_COOPMAT_BRIDGE=1
   cargo test -p wgpu-compute --test k24_coopmat on
   the bridged device. All three tests must EXECUTE
   (not skip): reference and K13 and K23 parity at
   6656 x batches 64/62, the 6656 full square, the
   band refusals. Any failure here stops the
   session: the mapping claim is wrong on the real
   driver and the note gets a correction record,
   not a tuning pass.
2. **Kernel-line A/B, interleaved**: prefill_profile
   at the 1,022-token prefill shape, arms K13
   (shipped), K23 (COOPMAT=1), K24 (COOPMAT=1,
   COOPMAT_V2=1), interleaved arm order, diag timing
   on: the k24_q4k_coopmat line against
   k23_q4k_coopmat's 16,951.3 ms and k13_q4k_mmq's
   4,250.1 ms over 2,912 dispatches, plus diag-off
   walls per arm. Report GB/s per arm.
3. **Session identity + golden** with COOPMAT=1 and
   COOPMAT_V2=1: the five golden prompts, identity
   against the shipped-default control, and the
   diag manifest must carry coopmat=true and
   coopmat_v2=true with k24_q4k_coopmat stamps in
   the capture.
4. **ACO autopsy of v2's compiled form** (the pass
   v1 never got): VGPR count, spills, scratch, and
   LDS for the K24 pipeline via pipeline executable
   properties or RADV shader stats, beside K23's
   for comparison, recorded in the verdict note.

Open items this lane does not close: the staging
prefetch split (named above); any Q5_K/Q6_K coopmat
form (K24 is Q4_K only, like K23); GFX11.5/12
element mappings; wave32 through the passthrough
(would need bridge work to request a subgroup size,
a separate lane's decision).

## Supersession (2026-11-07): the decision rule was met; both defaults flipped on

The card protocol above ran in full as leg 2 of
the wave20 consolidated session
(bench/wave20-session-2026-11-07.md, staged from
main 515ce23). Every leg of it discharged:

1. **Numeric gates**: tests/k24_coopmat.rs executed
   on the card, 3 passed, 0 failed, no skips. K24
   against the host reference at relative error at
   most 1.158e-6 (batch 62; batch 64 read 7.956e-7);
   against K13 at most 2.9e-7 relative. The wave64
   accumulator element mapping this note derived
   from Mesa source is PROVEN on the target card; a
   wrong mapping would have scrambled rows and
   columns and failed by a wide margin.
2. **Kernel-line A/B, interleaved** at the
   1,022-token prefill shape, 2,912 dispatches per
   arm: the k24_q4k_coopmat line ran 1,737.2 /
   1,751.9 ms (112 GB/s) against k13_q4k_mmq's
   4,021.0 / 4,046.5 ms (48 GB/s), about 2.3x
   faster; prefill walls 4,052 / 4,085 ms against
   6,307 / 6,401 ms, about 36 percent lower. The
   K23 v1 arm reproduced its standing verdict
   (16,900 / 16,963 ms): correct, about 4x slower
   than K13, never a default.
3. **Identity + golden** with COOPMAT=1 and
   COOPMAT_V2=1 (plus BRIDGE=1): IDENTITY PASS and
   GOLDEN PASS, the spec stream byte-identical to
   the golden stream, spec accounting (rounds=38,
   proposed=37, accepted=25) identical to the
   shipped-default control; the diag manifest
   carried "coopmat":"true", "coopmat_v2":"true".
4. **Autopsy**: K24 LDS 33,792 B (exactly the five
   staging arrays), VGPR 132 (not the 256 cap: the
   register-resident fold confirmed at the binary
   level), zero spills, zero scratch.

The decision rule stated at the top of the card
protocol (material kernel-line win over K13 with
speculative identity intact) IS MET. Under David's
standing order of 2026-11-07 (anything that makes
sense engine go faster should be set to on), the
flip lane `lane/coopmat-default-flip` moved BOTH

bench/coopmat-default-flip-2026-11-07.md: an unset
WGPU_COMPUTE_COOPMAT now arms the rung and an
unset WGPU_COMPUTE_COOPMAT_V2 now selects K24

decides on its own). The routing order and the
fallback chain are unchanged: a K24 refusal still
falls through to K23 by name, a K23 refusal to
K13, and a device without a coopmat pipeline

refusal on record. This section supersedes the

off" branch; the rest of this note stands as the
